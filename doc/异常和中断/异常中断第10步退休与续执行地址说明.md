# 异常与中断：第 10 步退休事件和架构续执行地址

> GitHub 发布说明（2026-10-10）：下文标为“仅本地”的历史档案/参考材料保留在开发机，未随本次源码发布；原验收结论和哈希不变。当前开发入口见 doc/CODEX_HANDOFF.md。

本步修改 [`mycpu_sync.v`](/D:/riscv/RISCV/myriscv/mycpu_sync.v)，为第 11 步精确中断提供 `arch_next_pc`。它表示**最后一条已提交指令之后，架构上应执行的地址**，复位值为 `0`。前端 `pc` 包含预取和重定向时序，不能直接充当中断 `mepc`。

## 指令后继地址

ID 在 `id_fire` 时确定本条指令的实际后继地址：普通指令及未采用分支为 `if_id_pc+4`；采用的 branch、JAL、JALR 为 `bj_pc`。JALR 的 `bj_pc` 已清除 bit 0。地址依次进入 `id_ex_next_pc`、`ex_mem_next_pc`、`mem_wb_next_pc`，与原指令的 valid、PC、异常标志同步推进；气泡和取消把对应字段清零。带异常的指令虽然经过流水级，但不会按此地址正常退休。

WB 的事件与寄存器更新如下：

| 事件信号 | 条件 | 时钟沿后 `arch_next_pc` |
|---|---|---|
| `normal_retire` | 有效指令，且不是异常、非法 CSR 或 MRET | `mem_wb_next_pc` |
| `sync_trap_event` | 同步异常或非法 CSR | `csr_trap_target`，即当前 Direct `mtvec` |
| `mret_commit` | 有效 MRET，无异常 | `csr_mret_target`，即 `mepc` |
| 无上述事件 | 气泡或流水线排空 | 保持原值 |

`normal_retire` 包含没有 GPR 写回的 branch、store、FENCE、合法 CSR 等，因而不能用 `debug_wb_rf_we` 代替。trap 和 MRET 与普通退休分开，避免一次指令产生两个退休事件。同步异常的故障指令本身不更新正常后继 PC；它直接将续执行地址设置为 trap 入口。上述事件目前是 CPU 内部信号，可由仿真和后续 SoC 集成层观察。

## 访存事件

`mem_store_request` 与 `ex_store_commit` 及 RAM 实际写使能同拍，表示 store 已在 EX/MEM 沿写入 RAM；它与随后 WB 的 `normal_retire` 是不同事件。`mem_load_request` 标记有效且无故障的 load 在 EX 发起访问；错误对齐或被较老异常挡住的 load 不产生该事件。当前 RAM IP **没有读使能端**，物理读口每拍都锁存地址，因此 `mem_load_request` 是有效 load 的架构请求标志，不代表 RAM 读端口停止了其他拍的读取。后续接总线时应把它接到明确的读请求握手上。

## 验证

`tb_retire_step10.v`（仅本地：`/D:/riscv/RISCV/difftest/tb/tb_retire_step10.v`） 复用第 9 步 ROM，每个时钟沿检查 `arch_next_pc`：未采用分支为 `PC+4`、采用 BEQ 为目标、JALR 清 bit 0 后为目标、自循环 JAL 为自身；六次 trap 进入 `0x180`，六次 MRET 返回 handler 更新的 `mepc`。气泡拍保持不变。测试还检查三类 WB 事件互斥、故障 load 不产生访存事件、store 事件等于 RAM 写使能。结果：`RESULT: PASS architectural next PC and separate retirement/memory events`。
