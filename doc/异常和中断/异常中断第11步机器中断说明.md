# 异常与中断：第 11 步三类机器中断

> GitHub 发布说明（2026-10-10）：下文标为“仅本地”的历史档案/参考材料保留在开发机，未随本次源码发布；原验收结论和哈希不变。当前开发入口见 doc/CODEX_HANDOFF.md。

本步在 [`mycpu_sync.v`](/D:/riscv/RISCV/myriscv/mycpu_sync.v) 接入 `irq_external`、`irq_software`、`irq_timer` 三路 **clk 域同步电平**。它们分别反映在 `mip.MEIP[11]`、`MSIP[3]`、`MTIP[7]`；`mip` 直接显示原始电平，即使全局 `mstatus.MIE` 或对应 `mie` 位关闭也能读到。CPU 不自动清除请求源。来自板级异步引脚的同步、窄脉冲保持，以及软件可清除的 MMIO 源留待 SoC 集成。

## 候选、排空与接受

每拍计算 `irq_eligible = mip & mie`，再用 `mstatus.MIE` 形成 `irq_candidate`。若多个源同时有效，仲裁为 **MEI > MSI > MTI**，对应 cause 11、3、7。候选到达 `FLOW_RUN` 的当拍就关闭 `id_fire`、保持前端，然后进入 `FLOW_IRQ_DRAIN`；先前已发射的指令继续经过 EX/MEM/WB 并正常提交。

当前 RAM/ROM 是固定一拍同步 IP。`pipeline_empty` 要求 ID/EX、EX/MEM、MEM/WB 全无有效指令，因此进入中断时已发射的 load/store 都已完成。将来总线支持可变延迟时，还需把总线 outstanding/响应状态加入排空判据；本步不能把现有条件直接用于 DDR3 总线。

排空后**重新读取** `mip/mie/mstatus`：请求已撤销或使能已关闭，就回到运行状态，原 ID 指令继续发射；仍有效才生成一次 `irq_take`。接受时，`csr_file` 写入 `mepc=arch_next_pc`、`mtval=0`、`mcause={1'b1,cause}`，保存旧 MIE 到 MPIE 并清 MIE；PC 和 `arch_next_pc` 同时转到 Direct `mtvec`。此时 `arch_next_pc` 来自最后一条真正退休的指令，不取可能超前的前端 `pc`。

若排空期间已发射的老指令报告同步异常，WB 的 `sync_trap_event` 优先进入同步 trap；中断源电平原样保留。CSR、ECALL/EBREAK 和 MRET 沿用串行控制；CSR/MRET 完成后经过 `FLOW_IRQ_CHECK`，用**更新后的** CSR 状态重判中断，未重判前不发射下一条指令。若 MRET 后源仍保持高电平，CPU 可以在恢复用户指令前再次进入同一个中断，处理程序或外设应清除源。

## 关键时序

| 时刻 | 前端 / 流水线 | 架构事件 |
|---|---|---|
| 候选首次出现 | ID 停止发射，IF/ID 与 ROM 地址保持 | 已发射指令继续执行 |
| 排空中 | EX/MEM/WB 按原顺序前进 | store 在 EX 沿写一次，后续在 WB 正常退休 |
| 排空结束 | 重新仲裁 pending 和使能 | 撤销则恢复；仍有效则 `irq_take` |
| `irq_take` 上升沿 | PC 重定向并清空旧前端 | 写 trap CSR；`mepc=arch_next_pc` |
| MRET 上升沿后 | 进入 `FLOW_IRQ_CHECK` | 先恢复 MIE，再决定是否重新进入中断 |

## 验证

`irq_step11.S`（仅本地：`/D:/riscv/RISCV/difftest/prog/irq_step11.S`） 与 `tb_irq_step11.v`（仅本地：`/D:/riscv/RISCV/difftest/tb/tb_irq_step11.v`） 检查八次中断和一次同步 load 非对齐异常：

- 三源同时 pending，关闭使能时 `mip=0x888` 可读；启用后依次响应 MEI、MSI、MTI，均在 PC `0x20` 进入，测试台逐个清源。
- 在 PC `0x24` 的故障 load 处拉高软件中断，先记录 cause 4、`mepc=0x24`、`mtval=0x301`；MRET 后才接受 MSI，`mepc=0x28`。
- 在 PC `0x28` 的 store 位于 EX 时拉高外部中断，写入及退休各一次，随后进入中断；外部电平保持到第一次 MRET 后，再次以同一 `mepc=0x2c` 进入。
- 在 PC `0x34` 的 store 位于 EX 时拉高并在排空中撤销定时器请求，无 trap；再分别在该 store 位于 MEM、PC `0x28` 的 store 位于 WB 时注入，确认接受时所有 store 请求与退休次数一致。
- 每次中断接受均检查流水线全空、无新的 ID 发射或访存请求、`mepc/mcause/mtval`、`mstatus.MIE`、处理入口 PC 与 `arch_next_pc`；最终核对 GPR 与 RAM。
