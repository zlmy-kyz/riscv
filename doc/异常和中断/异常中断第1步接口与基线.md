# 异常与中断：第 1 步接口和基线

本页固定首版设计选择。此步只新增共享定义与接口约定，**尚未将异常、中断或 CSR 接入 CPU**。后续步骤以 [`csr_defs.vh`](/D:/riscv/RISCV/myriscv/csr_defs.vh) 为唯一常量来源。

## 2. CSR 与异常常量

`csr_defs.vh` 集中定义首版实现的 CSR 地址、可写/输入位掩码、复位值、同步异常编号及机器中断编号。首版仅支持 M 模式、RV32I、无压缩指令，`mstatus.MPP=2'b11`、`mepc[1:0]=0`。`mstatus` 仅软件写 `MIE/MPIE`，`mie` 仅软件写 `MEIE/MTIE/MSIE`，`mip` 的对应三位取自中断输入，软件写无效。`misa=0x40000100`，`mstatush` 和机器信息 CSR 返回零；机器信息 CSR 包括后续审查补入的只读 `mconfigptr`（0xF15）。其余未声明 CSR 由后续合法性逻辑判为不存在。

同步异常：取指地址非对齐 0、取指访问失败 1、非法指令 2、断点 3、load 地址非对齐 4、load 访问失败 5、store 地址非对齐 6、store 访问失败 7、M 模式 ECALL 11。其中访问失败 1/5/7 预留给后续总线阶段，**当前 ROM/RAM 接口没有错误响应，不能实际产生这些异常**。机器软件、计时器、外部中断的原因分别为 3/7/11，`mcause[31]=1` 才表示中断。

## 3. Trap 入口与处理程序

- `mtvec` 复位入口设为 `0x00000100`，MODE 固定 `Direct(0)`；所有已实现 trap 跳到 `mtvec[31:2] << 2`。后续 CSR 模块可把复位入口做成参数，但应保持默认 `0x100`。
- 当前取指 ROM 地址为 `inst_sram_addr[11:2]`，可寻址 4 KiB；`0x100` 对应 ROM 字索引 `0x40`。后续 handler 链接到 ROM 地址 `0x100`，并为其留出空间；应用代码不得占用该区域。此步没有填充 handler。
- 复位取指 PC 仍为 `0x00000000`。后续 handler 需要在启动代码设置有效栈指针，并在进入中断前完成初始化。

## 4. 流水线事件接口约定

这些是后续阶段要实现的**单拍事件**，此步尚无对应 RTL 信号。事件只有在该操作实际发生时为 1，不能把流水寄存器的 `valid` 直接当作事件。正常事件均受 `resetn`、取消和异常状态约束。

| 事件 | 触发边界和语义 |
|---|---|
| `id_fire` | 某个有效 ID 指令在本拍被 ID/EX 接收一次。load-use 停顿、串行等待、IRQ 排空或取消时为 0；故障指令作为故障项进入 EX 时仍可为 1。 |
| `retire_valid` | WB 完成一条正常指令一次，包括不写 GPR 的 branch/store/CSR/MRET；异常项及气泡不退休。指令 PC、指令字和后继 PC 与事件同拍配对。 |
| `trap_valid` | 同步故障项在 WB 被接受，或中断在流水及在途事务排空后被接受，一次 trap 只脉冲一拍。与 trap PC、cause、tval 同拍配对；优先于普通重定向。 |
| `mret_valid` | 串行 MRET 在提交点执行一次，CSR 状态恢复并从最新 `mepc` 重取；它同时是一条正常退休指令。 |
| `mem_request_fire` | RAM/总线请求真正被接收一次。当前固定延迟 BRAM 中，store 的实际写使能在 EX 时钟沿为一次事件；未来总线中改为 `valid && ready` 握手，load 也按实际请求接收计数。停顿不能重复发请求。 |

### 事件信号的位宽、位置和落地状态

下表是第 1 步确定的**接口契约**；“已实现”表示截至第 3 步的代码状态，不改变上面记录的第 1 步基线。

| 信号 | 位宽 | 产生位置与消费方 | 截至第 3 步 |
|---|---:|---|---|
| `id_fire` | 1 | ID 发射控制产生；ID/EX 在该沿接收当前 IF/ID 项。 | 已实现，见第 3 步文档；串行项也只发射一次。 |
| `retire_valid` | 1 | WB 正常提交产生；计数器和 `arch_next_pc` 将消费。 | 尚未实现；`mem_wb_valid` 只说明 WB 有项，不能替代正常退休。 |
| `trap_valid` | 1 | 同步异常 WB 提交或排空后接受中断时产生；CSR 和 PC 控制将消费。 | 尚未实现；第 3 步仅预留重定向请求。 |
| `mret_valid` | 1 | MRET 在 WB 真正提交时产生；CSR 恢复和 PC 重定向将消费。 | 尚未实现；第 3 步仅识别串行占位项。 |
| `mem_request_fire` | 1 | EX 的 BRAM 请求实际发生时产生；未来总线改为请求握手成功。 | 尚未作为独立事件输出；现有 store 实际写使能在 EX。 |
| `arch_next_pc` | 32 | 正常退休或重定向更新；排空后接受中断时用于写 `mepc`。 | 尚未实现；当前预取 `pc` 不能代替它。 |

上述事件都是**时钟沿上的一次性事实**：同一指令即使在流水寄存器里保持多拍，也只能产生一次对应事件。`csr_file` 的 `trap_enter`、`mret_commit` 是未来由提交事件驱动的模块输入；它们不等同于单纯译码出 ECALL/MRET。

另预留 `arch_next_pc`：记录所有已正常退休指令之后的架构续执行地址，供排空后接受中断写入 `mepc`。普通顺序指令为 PC+4，采用跳转为目标；它不能直接取当前预取 PC 或 `debug_wb_pc`。异常指令不更新它。MRET 重定向后更新为返回地址。第 10 步接入并验收。

同拍控制以**年龄及提交结果**决定：老指令的同步异常阻止年轻指令副作用；trap/MRET 重定向高于前端 hold 和普通分支；在处理中断前先排空并重新检查 pending。具体优先编码在后续流水控制步骤实现。
