# CPU 原生 DDR 指令/数据争用验证

日期：2026-09-29。

## 目的与改动

确认 CPU 自身能否同时提出 DDR 取指和 DDR 数据请求，并在发生总线停顿时仍完成程序。上一轮真实片内 ROM/RAM＋DDR3 物理模型的 `ld_st` 通过，但该轮两路 DDR 请求重叠计数为 0；测试平台主动注入的物理模型争用另见 `DDR3复位与指令数据争用验证_2026-09-29.md`。

检查 `myriscv/mycpu_sync.v` 后可见，取指请求由 `fetch_valid`、单笔待响应和指令缓冲条件控制，不直接由 `data_pipeline_stall` 禁止；数据请求由 ID/EX 中的 load/store 产生，等待 ready 时保留字段。因此结构上允许两路请求同时有效，但具体是否出现取决于存储器时序。

新增 `source/tb_cpu_ddr_overlap_fast.v` 作为只观察的外层 TB：计数 CPU 原始两路请求、译码后的两路 DDR 请求、等待周期和指令获准次数；在桥空闲且两路同时有效时断言数据 ready=1、指令 ready=0。新增 `MyCpu_test/run_cpu_ddr_overlap_fast.py`，复用现有五个已暂存镜像并逐项保存独立日志。没有修改 CPU、互连、桥、片内 IP、PDS 配置或现有共享 TB。

为在真实 DDR3 物理模型中制造同一类 CPU 原生请求相遇，另新增 `source/tb_soc_ddr3_pds_ip_cpu_overlap.v` 和 `sim/pds_ddr_cpu_overlap_run.tcl`：在 CPU 从 DDR 取回 load/store 指令之后，只延后**下一次指令请求的 ready 握手**。指令和数据请求仍由 CPU 发出，并通过 SoC 地址译码器；在两路同时有效时撤除延后，检查桥的数据优先规则与程序最终结果。先在快速模型用 `source/tb_cpu_ddr_backpressure_fast.v` 验证同样的时序注入方法。

## 复现命令与实测结果

在工程根目录执行：

```powershell
python MyCpu_test/run_cpu_ddr_overlap_fast.py
python MyCpu_test/run_cpu_ddr_overlap_fast.py --backpressure ld_st
```

该脚本使用 Icarus 编译原 CPU、SoC 总线、DDR 桥和快速 DDR 用户口模型；`inst_rom`/`data_ram` 是 `source/tb_soc_ddr3_rv32i_mem.v` 的仿真装载源。镜像从 `MyCpu_test/ddr_stage/` 读取，脚本不会重新生成或改写镜像。第二条命令选择短暂取指反压用例并保存独立日志。2026-09-29 本轮五项均返回进程码 0、`tohost=1`，且观察到真正来自 CPU、经互连译码的两路 DDR 请求重叠：

| 程序 | DDR 两路同时有效周期 | 桥空闲时数据优先检查次数 | 指令请求获准次数 | 结果与日志 |
| --- | ---: | ---: | ---: | --- |
| `ld_st` | 387 | 387 | 1012 | PASS；`sim/cpu_ddr_overlap_fast_ld_st.log` |
| `lb` | 25 | 25 | 302 | PASS；`sim/cpu_ddr_overlap_fast_lb.log` |
| `st_ld` | 99 | 99 | 532 | PASS；`sim/cpu_ddr_overlap_fast_st_ld.log` |
| `sw` | 69 | 69 | 563 | PASS；`sim/cpu_ddr_overlap_fast_sw.log` |
| `lw` | 25 | 25 | 332 | PASS；`sim/cpu_ddr_overlap_fast_lw.log` |

`ld_st` 另记录指令请求等待 2104 周期、数据请求等待 726 周期，首个重叠的 DDR 局部地址为指令 `0x000001ac`、数据 `0x00003000`；程序仍通过。这证明 CPU 能产生并完成两路同时存在的访问，无需为快速模型另造一份程序镜像。

快速模型的短暂取指反压预检：用 `tb_cpu_ddr_backpressure_fast` 运行 `ld_st`，在 DDR 内存指令返回后延迟后续取指 ready 两拍，观察到 CPU 自发的指令/数据 DDR 请求同时有效（局部地址 `0x1a8`/`0x3000`），最后 `RESULT: PASS ld_st ... tohost=1 cycles=16014`。原始输出保存在 `sim/cpu_ddr_backpressure_fast_ld_st.log`。

真实片内 IP＋DDR3 物理模型的对应命令（从 `ipcore/ddr3/sim/modelsim` 目录执行）：

```powershell
& 'D:\modelsim\win64pe\vsim.exe' -c -do 'do D:/riscv/RISCV/sim/pds_ddr_cpu_overlap_run.tcl; quit -f'
```

独立日志 `sim/pds_ddr_cpu_overlap_ld_st.log` 的最终检查点：

```text
CHECK: ld_st CPU copied 1056 words then fetched from DDR
CHECK: held next CPU fetch after DDR memory instruction at pc=800001a4
CHECK: CPU-origin DDR overlap inst=000001a8 data=00003000 after 2 held cycles
RESULT: PASS ld_st DDR RV32I tohost=1 cycles=67254
Errors: 0, Warnings: 353
```

无 `RESULT: FAIL`。ModelSim 于 2026-09-29 16:17:02 结束，耗时 21 分 52 秒。真实片内 IP＋DDR3 物理模型下，两路请求确实由 CPU 同时提出，延后取指 ready 两拍后相遇；撤除延后时桥在空闲仲裁点选择数据请求，之后程序完成。现有 `ld_st` 镜像已同时包含 DDR 取指与频繁 load/store，因此无需新建程序并重新生成片内 RAM IP。

作为时序对照，未修改 RTL 的真实片内 IP＋DDR3 物理模型 `ld_st` 日志 `sim/pds_ddr_reset_ld_st.log` 记录重叠 **0**、重新装载 1056 字、`tohost=1`、ModelSim `Errors: 0`；`sim/pds_ddr_contention.log` 则记录 TB 注入到 SoC DDR 入口的真实物理模型争用通过、`Errors: 0`。两份物理模型日志属于上一独立验证步骤，本步没有重新运行它们，也不把注入的请求称为 CPU 自发请求。

## 结论与未覆盖范围

CPU 在较快的 DDR 用户口应答下确实会同时提出指令和数据 DDR 请求；所选五个程序在争用和等待后完成。真实 DDR3 IP 当前**自然时序**下的 `ld_st` 没有出现同周期两路请求；在 TB 将一次取指 ready 延后两拍的条件下，已于同一次真实片内 IP＋DDR3 物理模型联仿中验证 CPU 原生争用、数据优先和程序通过。这个结果证明指定反压场景，不代表自然时序必定发生争用。真实片内 IP 初始化内容是 PDS 生成参数的一部分，若以后加入新程序镜像，需要重新生成对应 IP 并另存测试日志。未覆盖连续数据请求长期压住指令请求的公平性，也未做实板验证。
