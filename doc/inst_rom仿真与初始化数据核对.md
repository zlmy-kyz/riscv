## 1. 结论速览

| # | 结论 |
| :-- | :-- |
| 1 | IP 核仿真**不需要额外的顶层模块**。testbench 本身是仿真顶层(无端口、是根节点),直接例化 IP 即为 DUT。 |
| 2 | "先写顶层再写 tb"只在**系统级**成立——那时例化的是真实顶层 `topcpu`,IP 在 `topcpu` 内部。两者是不同验证层次,不是二选一。 |

| 4 | 厂商模板 `inst_rom_tb.v` 的断言是"全 1 比对",对它当前固化的内容无效,不能当验收依据。 |

## 2. 两种验证层次

```
testbench(仿真唯一顶层,无端口)
   ├── 单元级:直接例化 inst_rom          → DUT = IP 核本身
   │     对应文件: source/tb_instrom.v、ipcore/inst_rom/inst_rom_tb.v
   └── 系统级:例化 topcpu,IP 在顶层内部   → DUT = CPU + 存储整体
         对应文件: myriscv/topcpu_tb.v + myriscv/topcpu.v
```

**只有当 IP 接口与 CPU 总线不匹配时才需要夹一层**:CPU 给的是 `[31:0]` 字节地址,`inst_rom.addr` 是 `[9:0]` 字地址,必须做 `byte_addr[11:2]` 切片。这层适配属于**设计代码**(综合也要用),应当做成独立模块再用 tb 去测,而不是在 tb 里临时拼线。

## 3. inst_rom 的接口与时序(仿真必须遵守)

| 端口 | 方向 | 位宽 | 说明 |
| :-- | :-- | :-- | :-- |
| `addr` | input | `[9:0]` | **字地址**,不是字节地址 |
| `clk` | input | 1 | 时钟 |
| `rst` | input | 1 | **同步、高有效**(注意不是低有效 `resetn`) |
| `rd_data` | output | `[31:0]` | 读出数据 |

- **读延迟 1 拍**:地址在 `clk` 上升沿被锁存,`rd_data` 在该沿之后有效。仿真中应在 `posedge` 之后 `#1` 采样(`-novopt` 下沿上存在竞争)。
- **复位期间** `rd_data = 0`。
- 容量 1024 × 32 bit = 4 KB,无写通道。

## 4. 自检测试台 `source/tb_instrom.v`

它做四件事:

1. **复位检查** —— `rst` 有效期间 `rd_data` 必须为 0;
2. **内容检查** —— 全 1024 地址读一遍,与黄金文件逐字比对;
3. **延迟检查** —— 若读到的值恰好等于"上一个地址的数据",判定读延迟不是 1 拍,与内容错误分开计数;
4. **结果导出** —— 实读数据写入 `sim/rom_dump.hex`,格式与 `rom_test.dat` 一致,可直接 diff。

关键参数(文件开头):

| 参数 | 默认值 | 说明 |
| :-- | :-- | :-- |
| `GOLDEN_FILE` | `D:/riscv/tbtb/rom_test.dat` | 黄金参考 |
| `DUMP_FILE` | `D:/riscv/RISCV/sim/rom_dump.hex` | 实读导出 |
| `CHECK_DATA` | `1` | 置 0 则只验复位与时序,跳过内容比对 |
| `CLK_HALF` / `RST_CYCLES` | `5` / `8` | 10 ns 周期、复位 8 拍 |

运行:

```bash
cd D:/riscv/RISCV/sim/ip_tb
vsim -c -do run_ip_tb.tcl
```

输出末尾会打印:

```
============================================================
 inst_rom 独立仿真报告
   复位检查 (rst 期间 rd_data = 0) : PASS
   内容检查 (1024 字逐字比对)     : ...
   读延迟检查 (应为 1 拍)          : PASS
============================================================
```

## 5. 初始化数据核对(重要)

### 5.1 数据的两条通路

| 通路 | 来源 | 内容 |
| :-- | :-- | :-- |
| A. IP 实际固化 | `ipcore/inst_rom/rtl/inst_rom_init_param.v` 的 `INIT_00_0_0` ~ `INIT_7F_0_0` | 生成 IP 那一刻的初始化数据 |
| B. 工程里的程序源 | `D:/riscv/tbtb/rom_test.dat` | 一行一个 32 bit 十六进制字,行号 = 字地址 |

`inst_rom.v` 第 103 行把 `c_INIT_FILE` 覆写成了 `"NONE"`,所以仿真/综合时用的都是 A,**B 只在"喂给 IP Compiler 的那一次"起作用**。A 与 B 一旦脱节,仿真比对必然失败。

### 5.2 打包规则(以 DRM 模型的实际读取方式为准)

`INIT_xx_0_0` 是 288 bit。DRM 的行为模型是这么读的(`GTP_DRM36K_E1.v` 初始化块 + `mem_read_a`):

```verilog
mem[cnt] = INIT_xx[cnt*9 +: 9];                      // cnt = 0..31
// 32bit 字 = { mem[4W+3][7:0], mem[4W+2][7:0], mem[4W+1][7:0], mem[4W][7:0] }
```

所以正确口径是:

```
288 bit = 32 个 9 bit 槽(每个槽低 8 位是有效字节)
每 4 个槽拼成 1 个 32 bit 字,槽号小的在低字节(小端)
一个字 = 一个地址的数据
地址 = INIT 序号 × 8 + 槽组号        (槽组号从最低 36 bit 起算)
```

128 个 `INIT_xx` × 8 = 1024 字,与 ROM 深度一致。

> ❌ 常见错误口径:**把 36 bit 槽直接当成 32 bit 字**(或"低 32 bit 是数据、高 4 bit 恒零")。这样读地址 0 会得到 `0x02800093`,而 DUT 实际读出的是 `0x00A00093` —— 见 5.3。

### 5.3 逐字比对结果

按 5.2 的正确口径解码 `inst_rom_init_param.v` 的 128 个 `INIT_xx_0_0`,与 `rom_test.dat` 逐字比对:

| 地址 | IP 固化 | `rom_test.dat` | 判定 |
| :--: | :-- | :-- | :--: |
| 0 | `0x00A00093` | `0x00A00093` | ✓ |
| 1 | `0x00508113` | `0x00508113` | ✓ |
| 2 | `0x002081B3` | `0x002081B3` | ✓ |
| 3 | `0x40118233` | `0x40118233` | ✓ |
| 4 | `0x00209293` | `0x00209293` | ✓ |
| 5 | `0x00328333` | `0x00328333` | ✓ |
| 6 | `0x0000006F` | `0x0000006F` | ✓ |
| 7~14 | `1,2,...,8` | `1,2,...,8` | ✓ |
| 15~1023 | `0` | `0` | ✓ |

**1024 个地址全部一致,不一致 0 个。**

行为级复核(用官方 `GTP_DRM36K_E1.v` 模型跑取指):`if_id_inst` 依次得到
`00A00093 / 00508113 / 002081B3 / 40118233 / 00209293 / 00328333 / 0000006F / 1 / 2 / 3 …`,与 `rom_test.dat` 完全吻合。

### 5.4 更正说明(2026-09-12)

本节早先给出过完全相反的结论("地址 0~5 不同、B 是修正后版本、IP 没跟着重新生成")。**该结论错误**,已在 2026-09-12 更正,原因与证据:

| 口径 | 地址 0 的解码结果 |
| :-- | :-- |
| 低 36 bit 槽直接截成 32 bit | `0x02800093` ← 旧文档用的口径(错) |
| 低 32 bit 直接截取 | `0x02800093`(同一个错) |
| **按 `mem_read_a` 规则解码** | **`0x00A00093`** ← DUT 实际读出值 |
| `rom_test.dat[0]` | `0x00A00093` ✓ |

当时的比对表里列出的"IP 固化值"`0x02800093 / 0x01410213 / …` 全部是错位读取的产物,由此推出的"操作数引用未定义寄存器、程序不自洽"也不成立。

### 5.5 处理方式

**不需要重新生成 IP。** ROM 里烧的就是当前程序。

只需要注意:`inst_rom` 是 `rst` **高有效同步复位**,不是 `resetn`;且它的**内部地址寄存器不带复位、输出在 `rst` 撤销后还被强制为 0 一拍**,接顶层时要按 `doc/取指ROM复位后丢第一条指令_原因与修复.md` 里的方式处理复位释放时序。

## 6. 顺带记录:厂商模板 `inst_rom_tb.v` 的两个坑

1. **断言口径错**:第 143 行 `check_err <= ({DATA_WIDTH{1'b1}} != tb_rddata);` 假设 ROM 内容全是 `32'hFFFFFFFF`。这个"全 1"来自生成器的示例初始化文件 `init_param_hex_exmp.dat`(整篇 `ffffffff...`),并非本工程的数据。
2. **`read_rom` 的入参没被使用**:`task read_rom(input read_rom)` 里的参数在整个 task 内无引用,`while (tb_addr < 2**ADDR_WIDTH)` 也无所谓"读什么"。
3. 初始化文件路径写死 `D:/riscv/tbtb/rom_test.dat`,换机器需注意。

因此**不建议**用厂商模板做验收,`source/tb_instrom.v` 才是本工程的验收依据。
