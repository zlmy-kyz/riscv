# 黄金轨迹差分验证：方法、落地与实测

> 对象：`myriscv/mycpu_sync.v`（module `mycpu_sync`）
> 环境：`difftest/`（iverilog + Python 黄金模型，全脚本化）
> 日期：2026-09-14

---

## 0 一句话

**先用一个独立实现的参考模型跑一遍程序，把每条指令的「PC + 写哪个寄存器 + 写什么值」记成
`golden_trace`；再让 myCPU 跑同一段程序，每写一次寄存器就和 `golden_trace` 比一次，
对不上就立刻打印现场并停止仿真。**

这件事的价值不在"能跑通"，而在**参考结果完全不依赖人手**：期望值由程序生成，
人只负责写测试程序，不参与任何一位的计算。本工程已经三次栽在"手算 RISC-V 编码"上
（见 `.workbuddy/memory/2026-09-13.md`），所以参考结果必须自动化。

## 1 整体结构

```
      prog/*.S
         │  ①汇编
         ▼
   ┌──────────────┐  ②指令级仿真(ISS)   ┌────────────────────┐
   │ rvtool.py    │────────────────────►│ rom.hex            │  程序镜像
   │              │                     │ trace.txt          │  写回轨迹（黄金）
   │  汇编+黄金模型│                     │ itrace.txt         │  指令流（黄金）
   └──────────────┘                     │ rf_golden.txt      │  寄存器堆终值
                                        │ mem_golden.txt     │  数据存储器终值
                                        └────────────────────┘
                                                   │
   myriscv/*.v ──┐                                 │
                 ├──► tb/tb_difftest.v ──── 每拍比对 ┘   不一致 → 打印现场 + $finish
   model/*.v ────┘      （存储器行为模型）
```

- **参考模型与 DUT 完全独立**：`rvtool.py` 是 Python 写的架构级 ISS，和 Verilog RTL 没有
  任何共享代码、没有共享常量表。这是差分验证成立的前提 —— 如果参考模型是从 RTL 抄来的，
  那就是自己给自己判卷。
- **黄金模型本身也要被验证**：`golden/selftest.py` 用两批**外部证据**校验它：
  ① 工程 ROM 里实际固化的 7 条指令（`doc/cpu/inst_rom仿真与初始化数据核对.md` 里已用官方
  GTP 行为模型复核过）；② 黄金模型在原程序上的行为与文档记录的实测取指序列。
  这一步失败就不许往下走。

## 2 采样点：整个方案最容易写错的地方

DUT 的 `debug_wb_*` 和 `if_id_*` 都是**组合直出**（来自 ID 级）。所以：

| 采样方式 | 采到的是 |
|---|---|
| `always @(posedge clk)` 读信号（= 沿前值） | **该沿正要提交的那条指令** ✅ |
| 沿后 `#1` 采样 | 下一拍才会提交的那条指令（整体错开一拍）❌ |

`tb_difftest.v` 用的是前者。这不是风格问题：`mycpu_sync.v` 里
`if_id_inst/if_id_pc` 是 ID 级的输入寄存器，`rf_we`/`rf_waddr`/`rf_wdata` 由它组合派生，
寄存器堆在同一个沿上完成写入 —— 沿前值恰好就是"这次写入的指令"。

### 两个副作用

1. **x0 不能算写回**。`jal x0, halt` 这类指令 `rf_we` 是真的拉高的，但架构上不写 x0。
   DUT 侧已门控：`debug_wb_rf_we = {4{rf_we & (rf_waddr != 5'd0)}}`；
   黄金模型侧天然只记 `rd != 0`。两边口径必须一致，否则第一次比对就会假失败。
2. **一条指令在 ID 停多拍时要去重**。load 修复版会让 load 在 ID 占两拍，那两拍的
   `if_id_pc` 相同。测试台的去重规则是"PC 相同且中间没有气泡 → 只比第一次"；
   中间出现气泡（`if_id_valid=0`）则清掉去重状态，允许同一 PC 再次出现
   （分支跳回原处是合法的）。

## 3 三路比对，各有分工

| # | 比对内容 | 触发条件 | 能抓到什么 |
|---|---|---|---|
| 1 | **写回轨迹** `{pc, wnum, wdata}` | `debug_wb_rf_we != 0` | 运算结果错、写错寄存器、漏写/多写 |
| 2 | **指令流** `{pc, inst}` | ID 级 `if_id_valid=1` | 取指错、分支目标错、冲刷漏冲/多冲、PC 错位 |
| 3 | **终值** 寄存器堆 + 数据存储器 | 停机后整体导出比对 | 数据通路与存储器互动的整体一致性 |

第 2 路是这套方案比"只比写回"更值钱的地方，下面这个真实例子说明得很清楚。

### 3.1 为什么"只比写回"会骗人

`prog1_mem.S` 开头：

```asm
addi x1, x0, 0x40
addi x2, x0, 0x123
sw   x2, 0(x1)      # mem[0x40] = 0x123
lw   x3, 0(x1)      # 读回 -> 应该是 0x123
addi x4, x3, 1
sw   x4, 4(x1)
lw   x5, 4(x1)      # 读回 -> 应该是 0x124
...
```

原版 RTL 的 load 有"取到上一个地址数据"的 bug，但前两条 `lw` **侥幸是对的**：
`data_ram` 的地址口是 `alu_result` 组合直连，而 `lw` 前面那条 `sw` 用的地址恰好也是
`0x40`/`0x44`，于是"上一个地址"正好就是自己要读的地址。

真正暴露它的是循环里的 load：

```asm
_l:
        lw    x19, 0(x1)     # @pc=0x60，前一条是 blt，地址口残留的不是 0x40
        addi  x17, x17, 1
        blt   x17, x18, _l
```

差分验证报出来的是：

```
[FAIL] 写回内容不一致 @pc=00000060 —— 第 18 次写回
       DUT : x19 <= 00000000
       黄金: x19 <= 00000123
```

**覆盖不到的地方，比对器再严也没用。** 所以测试程序要专门去构造"地址与前一条指令不同"
的访存序列，而不是顺着写好就算。

## 4 停机与失败

- **停机标记**：`jal x0, self`（自环跳转）。黄金模型遇到它就记录 `halt_pc` 并收工；
  RTL 侧测试台看到 ID 级的 PC 等于 `halt_pc` 就导出终值、判 PASS。程序必须以它结尾。
- **失败动作**：打印「第几次写回 / 第几条指令 + DUT 值 + 黄金值」，然后 `$finish`。
  直接可以拿去做二分定位；要波形就 `-Wave` 出 `wave.vcd`。
- **跑飞保护**：拍数上限 `MAX_CYCLE`（默认 20000）。超时不是"挂死"，而是明确报
  `[FAIL] 超过 N 拍仍未到停机点` 并打印当前 ID 的 PC/指令。
- **结束时的一致性检查**：到停机点时如果 `it_i != n_it` 或 `wb_i != n_wb`，说明有漏执行/
  漏写回，报 `[FAIL] 已到停机点，但轨迹没走完`。

## 5 实测结果

```
                                                （difftest\_matrix.log）
prog0_alu / 原版 mycpu_sync                  => PASS  (exit=0)
prog1_mem / 原版 mycpu_sync                  => FAIL  (exit=1)
      [FAIL] 写回内容不一致 @pc=00000060 —— 第 18 次写回
prog0_alu / loadfix                          => PASS  (exit=0)
prog1_mem / loadfix                          => PASS  (exit=0)
```

| 程序 | 覆盖 | `mycpu_sync.v`（原版） | `mycpu_sync_loadfix.v` |
|---|---|---|---|
| `prog0_alu` | R 型全 10 条 / I 型 6 条 / 移位 3 条 / lui / auipc / 6 条分支（命中+不命中）/ jal / jalr / 累加循环（背靠背 RAW） | **PASS**<br>78/78 条指令、54/54 次写回、98 拍<br>寄存器堆 32 项 + 数据存储器 1024 项终值全一致 | **PASS** |
| `prog1_mem` | 在 prog0 基础上加 sw/sh/sb + lw/lh/lb/lhu/lbu，含"load 结果驱动分支"的依赖链 | **FAIL** @pc=0x60 | **PASS**<br>32/32 条指令、23/23 次写回 |

两个结论：

1. **prog0 PASS 说明 CPU 的主干是对的**：取指、分支冲刷、译码、立即数生成、ALU 十一种运算、
   jal/jalr 链接值与目标、写回时机，全部与架构语义一致。`doc/cpu/mycpu_sync代码问题清单.md` 里
   当年那批功能性怀疑（D 项分支不跳、G 项 alu 编码错位等）已经全部不成立。
2. **prog1 FAIL 定位到唯一一个真问题**：load 没算 `data_ram` 的 1 拍读延迟。

## 6 顺带修掉的两件事

### 6.1 debug 观测口是隐式 1 位线网（必须修，否则方案没法落地）

`mycpu_sync.v` 原文末四行只写了 `assign debug_wb_* = ...`，**没有声明**。iverilog 按
"隐式 1 位线网"处理，32 位的 `pc` / `wdata` 被截成 1 位，观测口等于废掉：

```
mycpu_sync.v:261: warning: implicit definition of wire 'debug_wb_pc'.
mycpu_sync.v:262: warning: implicit definition of wire 'debug_wb_rf_we'.
mycpu_sync.v:263: warning: implicit definition of wire 'debug_wb_rf_wnum'.
mycpu_sync.v:264: warning: implicit definition of wire 'debug_wb_rf_wdata'.
```

改法（已合入 `myriscv/mycpu_sync.v`，备份在 `.workbuddy/backup/mycpu_sync_20260914_before_difftest.v`）：
把这四个信号**提成模块端口**（端口即声明，位宽由接口保证），并把 `rf_we` 按 `rd != 0` 门控：

```verilog
module mycpu_sync (
    input  wire        clk,
    input  wire        resetn,
    output wire [31:0] debug_wb_pc,
    output wire [3:0]  debug_wb_rf_we,
    output wire [4:0]  debug_wb_rf_wnum,
    output wire [31:0] debug_wb_rf_wdata
);
...
    assign debug_wb_pc       = if_id_pc;
    assign debug_wb_rf_we    = {4{rf_we & (rf_waddr != 5'd0)}};   // x0 不算写寄存器
    assign debug_wb_rf_wnum  = rf_waddr;
    assign debug_wb_rf_wdata = rf_wdata;
```

这是**纯观测性**改动，对 CPU 行为零影响（`regfile` 本来就忽略 `waddr==0` 的写入）。

### 6.2 load 修改（参考实现，未合入工程）

文件：`difftest/rtl/mycpu_sync_loadfix.v`（可跑、已通过全部测试）。
与 `mycpu_sync.v` 的差异只有 4 处：

```verilog
// ① 新增两拍状态机
reg mem_wait;
always@(posedge clk)begin
    if(!resetn)                   mem_wait <= 1'b0;
    else if(mem_wait)             mem_wait <= 1'b0;
    else if(i_l && if_id_valid)   mem_wait <= 1'b1;
end
wire mem_start = ~mem_wait & i_l & if_id_valid;   // 发地址拍
wire mem_data  =  mem_wait;                       // 取数拍
wire mem_hold  =  mem_start;                      // 冻结 pc / IF-ID / ROM 地址口

// ② 取指地址 + pc 一起冻结（两者必须同时冻，理由见下）
assign inst_sram_addr = mem_hold ? pc : (valid ? next_pc : pc);
...
    else if(valid) pc <= mem_hold ? pc : next_pc;

// ③ IF/ID 新增一个冻结分支（放在 flush 分支之前）
    else if(mem_hold)begin
        if_id_inst  <= if_id_inst;
        if_id_pc    <= if_id_pc;
        if_id_valid <= if_id_valid;
    end

// ④ 发地址那一拍不写回
assign rf_we = gf_we & if_id_valid & ~mem_start;
```

时序：load 从 1 拍变 2 拍 —— 拍 0 送地址（不写回），拍 1 数据已出来（沿上写 RF）。

### 6.3 写这个补丁时踩的两个坑（都是差分验证当场抓出来的）

**坑 1：多插了一个气泡，把该跑的指令冲掉了。**

第一版按"load-use 要停一拍"的直觉，在取数拍的下一个沿插了气泡。结果验证报：

```
[FAIL] 指令流不一致 —— 第 4 条有效指令
       DUT : pc=00000014 inst=0040a223
       黄金: pc=00000010 inst=00118213
```

`0x10` 那条指令被永久跳过。原因：**这个设计根本不存在 RAW 冒险。**
它只有 IF/ID 一个流水边界，生产者在"自己 ID 那拍末尾的沿"写寄存器堆，
消费者在"下一拍 ID"组合读 —— 非阻塞赋值在该沿已完成，消费者当拍就能读到新值。
load 多停一拍后，消费者正好落在写回沿之后的那一拍，天然对齐，**既不用前递也不用气泡**。
（这与 `.workbuddy/memory/2026-09-13.md` 里"本工程当前不存在 RAW 冒险"的结论一致。）

**坑 2：只冻 IF/ID 不冻 pc，取指流错位。**

第二版想让 pc 照常 +4、只把 IF/ID 钉住。结果同样报 `0x14` 覆盖了 `0x10`。
原因：IF/ID 在沿上锁的是 **(pc, mem[pc]) 这一对**，
`inst_if` 每一拍提供的正是 `mem[pc]`。只冻 IF/ID 不冻 pc，
下一拍的交付就变成 `(pc+4, mem[pc+4])`，中间那条指令被跳过。

> 附带一条不变式，改取指侧时务必守住：
> **`inst_rom` 内部地址寄存器 == `pc`（两者每拍锁同一个 `next_pc`）。**
> 一旦为了 stall 去改 `inst_sram_addr` 却不改 pc（或反过来），这个锁步立刻破裂。
> 第一版把 `inst_sram_addr` 门控成 `pc`、pc 却照常前进，取指就整体错位了。

## 7 为什么用行为级存储器模型

| | 行为模型（本环境） | 厂商 `ipcore/` IP |
|---|---|---|
| 工具 | iverilog（本机可用） | vsim / ModelSim（Pango 库是编译好的 `.qdb`，**没有 `.v` 源文件**） |
| 换程序 | 改 `rom.hex` | 必须重新生成 IP 的 `INIT_xx` 常量 |
| 用途 | 日常功能回归 | 上板前最终时序签核 |

`model/inst_rom.v` 与 `model/data_ram.v` 的时序**照真 IP 的实测结论写**，不是简化版：
1 拍同步读、`OUTPUT_REG=0/FAB_REG=0` 下数据不是"再打一拍"、ROM 内部地址寄存器不复位、
**ROM 输出在 `rst` 撤销后仍被强制为 0 一个时钟**。最后一条即
`doc/cpu/取指ROM复位后丢第一条指令_原因与修复.md` 里那个坑的根源，本模型保留了它 ——
所以它比"乐观模型"更悲观。实测下 `mycpu_sync.v` 的 `valid`（复位延迟一拍）+ 地址口门控
正好把这个额外拍吸收掉，复位后第一条指令 `(0, mem[0])` 正确取出、0 丢指令。

最终签核仍应在 vsim + 真 IP 上复跑同一套黄金轨迹（换法见 `difftest/README.md` 第 6 节）。

## 8 复用清单

```powershell
cd D:\riscv\RISCV\difftest

python golden\selftest.py                       # 0) 先确认黄金模型可信
.\run.ps1 -Prog prog0_alu                       # 1) 不访存覆盖
.\run.ps1 -Prog prog1_mem                       # 2) 含访存覆盖

```

新增测试程序 → 放进 `difftest/prog/*.S`，以 `halt: jal x0, halt` 结尾，直接
`.\run.ps1 -Prog <名字>`。可用指令集与语法限制见 `difftest/README.md` 第 5 节。

### 本机工具注意事项

- **bash 工具不可用**（用户名含单引号，shim 崩），一律用 PowerShell。
- PowerShell 抓不到原生命令的 stdout：需要 `| Out-String` 后
  `Set-Content -Encoding ASCII/UTF8` 落盘再读。
- 原生程序 stderr 经管道会被包成 ErrorRecord，脚本里
  `$ErrorActionPreference` 必须是 `Continue`（否则一行普通编译告警就会被当成异常抛出）。
- iverilog：`D:\iverilog\bin\iverilog.exe` / `vvp.exe`，统一 `-g2012`。
- IP 的 `*_init_param.v` / `*_Reset_Value.v` 是被 `include` 的，**不要**当源文件列进命令行，
  否则报 localparam 重复定义。
