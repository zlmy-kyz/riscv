## data_ram 写入 bbbbbbbb 而非 aaaaaaaa 的定位

用户问：tb 中 100ns `wr_data=bbbbbbbb`、120ns `wr_en=1`+`wr_data=aaaaaaaa`，为何写进去的是 `bbbbbbbb`。

用 iverilog + Pango 官方 `GTP_DRM36K_E1.v` 在 `.workbuddy/sim_dram/` 一比一复现，定位三个叠加因素：

- **A（真问题）**：tb 在复位撤销边界窗口内改 `wr_data`。IP 内部 `rsta_int` 比 `resetn` 晚一拍才撤销（100ns→100.2ns），导致首次采样失配。
- **B**：IP 内部 `csa_reg` 是**独立一级**寄存器（`GTP_DRM36K_E1.v:718`），只在 `CSA==CSA_MASK` 时更新；而 `da_reg/wea_reg/ada_reg` 在 `if(CEA)` 块内、CEA 恒 1，每拍都更新。CS 未初始化时 `csa_reg` 恒 `x` → 失去对齐。
- **C（仿真假象）**：IP 生成代码 `rtl/ipm2l_spram_v1_8_data_ram.v:303` 的 `always@(*)` 在本配置（DRM_DATA_WIDTH=32、CS_ADDR_WIDTH=0）下只赋常量、无敏感信号，iverilog 判定"永不触发"，导致 `cs_bit*/CSA/csa_reg` 恒为 `x`、`write_en_a` 恒 0，掩盖了 B。加 `initial` 补 CS 初值后症状精确复现，证明是纯仿真假象。

**修复验证通过**：避开复位撤销那一拍、并让 `addr`/`wr_data` 提前 `wr_en` 至少 1 拍建立后，读回 addr=1 = `aaaaaaaa` ✅

产出：`doc/data_ram写入数据错拍_bbbbbbbb问题.md`；复现工程 `.workbuddy/sim_dram/`（`tb_dram.v`、`src/ipm2l_spram_FIXED.v`、`tb_fixed.v`、`dram_fix.vcd`、trace 脚本）。

**关键结论（与 09-11 inst_rom 问题同源）**：Pango DRM 系列 IP 的复位都是"外部撤销后内部再同步一拍"，CPU 侧必须让复位晚一拍释放。

### 更正（用户质疑后）
用户指出 `always@(posedge clk)` 采到的是沿前稳定值，120ns 沿本该采到 `aa`——**用户正确**。原表述"数据比控制晚一拍"不准确。正确机制是 `csa_reg` 与 `da_reg/wea_reg/ada_reg` **更新条件不同**，CS 恒 `x` 时失去对齐。修好 CS 后三者同沿同步，写入正确。

### 用户当前 CPU 接法（结论）
读/写使能、地址、写数据**四信号全部组合直连 data_ram、同出 EX 级**。
**不存在错拍问题，无需修改**：四信号同源同拍、共享同一通路到 RAM；加法器最慢只影响时序（压频率），逻辑上严格对齐。
只有**混搭**（地址直连 + 使能寄存）才会错拍。需盯：① EX 级 stall 时四信号整体冻结；② 读写共用同一套 EX 信号以天然对齐一拍延迟。

## 给 myriscv/mycpu_sync.v 补上跳转地址 / next_pc 逻辑（用户请求）

`mycpu_sync.v` 已比上面那份复核稿新：`valid` 拼写已改对、`data_ram` 已例化、`regfile` 的 `rst_n` 已改成 `rst`。**剩下的就只有复核稿的 D 项**——`next_pc = pc+4` 写死，`b_pc`/`br_taken`/`imm_j` 无消费者。

改动（只动这一处，原有取指时序与所有译码一字未动）：

```verilog
wire [31:0] pc4    = pc + 32'h4;                  // 顺序后继,兼 jal/jalr 链接值
wire [31:0] b_pc    = pc + imm_b;                 // B 型分支目标
wire [31:0] jal_pc  = pc + imm_j;                 // J 型 jal 目标
wire [31:0] jalr_pc = (rdata1 + imm_i) & ~32'h1;  // I 型 jalr:(rs1+imm_i) 清 bit0
wire [31:0] bj_pc   = inst_jalr ? jalr_pc : inst_jal ? jal_pc : b_pc;
wire        pc_sel  = br_taken | inst_jal | inst_jalr;
assign      next_pc = pc_sel ? bj_pc : pc4;
```

- 原 `assign next_pc = pc + 4;`（在 pc 声明处）**下移**到这段之后，只留 `wire[31:0] next_pc;` 声明；`inst_sram_addr = valid ? next_pc : pc` 与 `pc <= next_pc` 都不动 → 地址口天然跟着跳，**分支零气泡**。
- `br_taken` 可安全相或：`br_alu` 对非分支指令 `inst_6b` 全 0 → 输出必 0。
- 位置：`mycpu_sync.v` 第 52–71 行（`pc4/b_pc` 原位扩写）。

**验证（`.workbuddy/lint_tmp/`，工程外）**：`tb_jump.v` + 自写 ROM 模型 + `data_ram_stub.v`，iverilog 跑 **24/24 PASS**（`run_jump.log`）：
- pc 轨迹 `0 → 4 → 0x10 → 0x18 → 0x20 → 0x24 → 0x28 → 0x2C → 0x30 → 0x34`；
- taken：`beq +12` / `jal +8` / `jalr 0x20` 全部命中目标，被跳过地址用哨兵字确认为 0；链接值 `x5=0x14`、`x7=0x1C` 正确；
- not-taken：`bne x1,x1,16`、`beq x1,x2,20` 正确落下一拍。
- 编译 0 error；仅剩复核稿 A/J 项那 8 条 `debug_wb_*` / `data_sram_*` 隐式线网告警（未在本任务范围内）。

**踩到并记录的两个坑**：
1. **ROM 模型必须是 1 拍延迟**（`always@(posedge clk) rd_data <= mem[addr];`）。第一版我写成 `a_r<=addr; rd_data<=mem[a_r];`（=2 拍），导致 `inst` 与 `pc` 差两拍、分支全乱。依据：`inst_rom.v` 的 `OUTPUT_REG=0`、`FAB_REG=0` → 读通路里只有那一个地址寄存器（见 `doc/ROM与RAM时序处理方案总结.md` 6.3）。
2. **手算 RISC-V 立即数编码极易错**：B 型的 `imm[4:1]` 放进 `inst[11:8]`，我按 `imm` 本位序填导致 `beq +12` 被编成 `+24`；`imm_i` 是 12 位**符号扩展**，`0x999` 实为 `0xfffff999`。测试程序里务必用互不相同的哨兵值，否则踩到 filler 也看不出来。

## 给 myriscv/mycpu_sync.v 加分支冒险（ID 级判定 + 冲刷 + 重定向）

用户要求"来写分支冒险"，选定：**改 mycpu_sync.v / ID 级组合判定 / 只做分支冒险（不碰 RAW）**。

**前置判断（重要）**：原文件严格说是单周期——`inst` 是 ROM 组合输出、`br_taken` 当拍出结果，**根本不存在冒险**。真正的切入点是文件里那两行作者自留注释：
`// 分支目标(if_id_pc→pc,差异1)` 与 `// 顺序后继 = jal/jalr 链接值(差异2)`
—— 作者早就标出"分支应当用 `if_id_pc` 而非 `pc`"这个一拍差。所以本次改动的实质是：**把 ID 级从"组合直通的 `inst`"真正切到 `if_id_inst` 上**，冒险才真实存在。

改动（`.workbuddy/branch_hazard/` 内有改前备份 `mycpu_sync_before_hazard.v`）：

1. ROM 输出改名 `inst` → `inst_if`（IF 级原始指令）；新增 `wire [31:0] inst = if_id_inst;`
   —— **沿用旧名的别名技巧**：下方 60+ 行译码/立即数代码一行都不用改。
2. IF/ID 寄存器加第三个分支：`else if(flush)` → `if_id_valid<=0`（`if_id_inst` 填 NOP `0x13` 兜底、`if_id_pc` 填哨兵 `FFFF_FFFF`，便于波形认气泡）。
3. 跳转逻辑全部改成 ID 级基准：`pc4/b_pc/jal_pc` 用 `if_id_pc`；`jalr_pc=(rdata1+imm_i)&~1` 不变（`rdata1` 本来就来自 `if_id_inst` 的 rs1）。
   `wire id_taken = br_taken|inst_jal|inst_jalr; wire flush = id_taken & if_id_valid;`
   `assign next_pc = flush ? bj_pc : pc + 32'h4;`
4. `alu_src1` 的 auipc 分支 `pc` → `if_id_pc`；`debug_wb_pc` → `if_id_pc`。
5. **出口闸门换成当级 valid**：`rf_we = gf_we & if_id_valid`、`data_sram_we = st_we & {4{if_id_valid}}`（原来乘的是复位延迟信号 `valid`）。

**实测（`.workbuddy/branch_hazard/tb_branch_hazard.v` + `run_bh.log`，iverilog 全 PASS）**：
- ID 级实际执行路径 = `0 → 4 → 0x10 → 0x18 → 0x20 → 0x24 → 0x28 → 0x2C → 0x30`，与预期完全一致；
- **错路指令一条都没落地**：3 条被冲掉的地址上放了哨兵指令（`0x22200A13` 等），断言"哨兵带着 valid=1 进 ID"报错 **0 次**，且 `x20~x23` 全 0；
- 气泡 **4 = 分支冲刷 3 + 复位 1**（3 条命中分支/跳转各付 1 个）；复位那 1 个是文档 4.5 已定性的"方案二固有 1 气泡"；
- 链接值 `x5=0x14`、`x7=0x1C`（均 = `if_id_pc+4`）；`bne`/`beq` 未命中正确顺延（`x24=0xfffff999`、`x25=0xfffffaaa`）。
- `-Wall` 静态检查 **0 error**，只剩改动前就有的 4 条 `debug_wb_*` 隐式线网（旧清单 A/J 项，未做）。

**顺带的一个好处**：分支比较的起点由"ROM 输出（tCO+阵列）"变成了"IF/ID 触发器"，IF 侧关键路径其实**变短了**——`next_pc` 现在不再串在 ROM 输出后面。

**留给下一步的两件事**（本任务明确不做）：
- **RAW**：ID 级分支操作数直接来自寄存器堆，前面刚写回的值读不到 → 分支判错且不可恢复（比数据通路错更严重）。
- 无静态预测（predict-not-taken）：命中分支一律付 1 个气泡。

## 固化:立即数统一生成(用户要求"简化 alu_src2,把立即数合到一起")

**结论:可以,而且顺带把分支目标也统一了。** 三处改动(`mycpu_sync.v`):

1. 新增唯一一个 `imm`(六类编码按位或,互斥前提写在注释里):
```verilog
wire imm_i_sel = i_I | i_l | inst_jalr;      // jalr 目标也吃 I 型立即数
wire [31:0] imm = ({32{i_u}}       & imm_u)
                | ({32{imm_i_sel}} & imm_i)
                | ({32{inst_s}}    & imm_s)
                | ({32{i_shamt}}   & shamt)
                | ({32{inst_b}}    & imm_b)
                | ({32{inst_jal}}  & imm_j);
```
2. `alu_src2` 由 5 级优先级链 → 2:1 选择:
```verilog
wire use_imm = i_u | i_I | i_l | inst_s | i_shamt;
wire [31:0] alu_src2 = use_imm ? imm : rdata2;
```
3. 分支目标复用同一个 `imm`(**省掉一个加法器 + 一层 mux**),`b_pc`/`jal_pc` 两个 wire 删除:
```verilog
wire [31:0] jalr_pc = (rdata1 + imm) & ~32'h1;
wire [31:0] bj_pc   = inst_jalr ? jalr_pc : (if_id_pc + imm);
```

**互斥性论证(能否直接"或"的前提,已写进 RTL 注释)**:U(0110111/0010111)、I(0010011/0000011)、S(0100011)、B(1100011)、J(1101111)、jalr(1100111) opcode 各不相同;唯一共用 0010011 的 `i_I` 与 `i_shamt` 由 funct3 区分(I 用 000/010/011/100/110/111,shamt 用 001/101)。

**实测**:`.workbuddy/imm_gen/tb_imm.v` + `run_imm.log` → **PASS**,八类全过:lui `0x12345000`、auipc `0x04+0x1000=0x1004`、addi 负数符号扩展 `0xFFFFFFFF`、slli/srli 移位量、sw 地址 `0+8`、lw 地址 `0+4`。
**回归**:原 `tb_branch_hazard.v` 一字未改重跑 → 仍 **PASS**(路径/气泡数/链接值全同),证明目标逻辑统一是等价的。日志在 `.workbuddy/imm_gen/run_bh_regress.log`。

## ⚠️ 更正上一节的判断:本工程**当前不存在 RAW 冒险**

我上一节说"RAW 比分支更危险、下一步必须做"——**对当前这版 RTL 是错的**。`tb_imm` 里 `addi x13,x12,1` 紧跟在 `addi x12,x0,-1` 之后,实测 `x13 = 0`(即正确读到 `0xFFFFFFFF`)——**背靠背也没有 RAW**。

原因:本设计的流水边界**只有 IF/ID 一处**,ID→EX→MEM→WB 全是同一拍组合逻辑。生产者在自己 ID 那拍**末尾的沿**写 RF,消费者在**下一拍**ID 组合读 RF → 天然错开一拍,永远读得到新值。**这是"2 级流水"的固有性质,不是巧合。**

→ 所以:**只有当真的插入 `id_ex_*` / `ex_mem_*` / `mem_wb_*` 打拍、把 WB 推到 ID 之后 ≥2 拍时,RAW 才成立**,那时才需要转发/停拍。用户选的"只做分支冒险"恰好就是完整的集合。
(对照:`topcpu_instrom.v` 那版**已经**有四级打拍,但还没有译码/RF/ALU,所以它将来一接数据通路就会立刻遭遇 RAW。)
