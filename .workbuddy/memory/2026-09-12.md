## 解答:RISC-V 异常与中断机制(纯知识问答,未改动任何 RTL)

用户问 4 个点:怎么实现 / 几个状态寄存器 / 有哪些异常与中断 / 引入流水线后会怎样。给出口径:

- **状态寄存器数量口径**:严格意义的"状态寄存器"只有 1 个 `mstatus`(MIE/MPIE/MPP);跑通 trap 最小需要 **8 个 CSR** = mstatus + mtvec + mcause + mepc + mtval + mie + mip + mscratch。misa/mcycle/minstret/counteren 均为可选。
- **mcause 编码**:bit31=1 中断、=0 异常;低 31 位原因码。示例:ecall(M)=0x0000_000B,机器定时器中断=0x8000_0007。
- **trap 硬件 5 动作**(同沿原子):mepc←PC / mcause←原因 / mtval←地址或指令 / mstatus.MPIE←MIE、MIE←0、MPP←当前特权级 / PC←mtvec(Direct)或 base+4×cause(Vectored);mret 反向恢复。
- **易错语义**:异常 mepc = 出错指令自身 PC;中断 mepc = 下一条未执行指令的 PC。
- **中断受理两道门**:`mip & mie != 0` 且 `mstatus.MIE=1`。
- **流水线引入后的 6 个麻烦**:①精确异常需"标记随指令流动 + 提交点统一处理";②同拍多异常按最老指令优先(WB>MEM>EX>ID>IF);③异常指令不能有副作用(we 与 `valid && !exc` 相与),这是把写操作集中到 WB 的最大收益;④中断只能落在指令边界且要选"下一条指令 PC";⑤trap 冲刷与分支冲刷共用 valid 清除通路;⑥阻塞(stall)期间不得受理中断,否则中断返回后重复执行——与教材分支那节"br_taken_cancel 必须在 RAW 相关解除后才有效"是同一个坑。
- **IP 中断源清零**:定时器靠软件写 mtimecmp,外部靠 PLIC claim/complete。

## 解答:取指 ROM 复位后丢失第 0 条指令(topcpu 直连 ROM 的仿真现象)

用户现象:复位 95ns 释放,100ns 处 `debug_pc/debug_inst` 期望 `(00000000, 00A00093)` 实测 `(00000000, 00000000)`,之后一一对应。

**结论:不是 IP 坏了,是"addr=next_pc 的接法 + IP 同步复位时序"不匹配。**

根因三条(全部有 RTL 依据,`GTP_DRM36K_E1.v`):
1. `addr = next_pc = pc+4`,而复位期间 `pc=0` → ROM 地址端口**在整个复位期间就是 word 1**;word 0 从没被寻址过。
2. **ROM 内部地址寄存器 `ada_reg` 不带复位**(第 711–725 行 `always @(posedge CLKA) ... ada_reg <= ADDRA;` 无 rst 分支),复位期间照常锁存 → 复位结束时已指向 word 1。
3. 输出受 `rsta_int` 控制(第 1143–1149 行),而 `rsta_int` 是 `RSTA` **打了一拍**(第 1433–1440 行)→ `rst` 撤销后输出还被强制为 `RSTA_VAL(=0)` 一个时钟。所以 100ns 那拍 `rd_data=0`,IF/ID 锁到 `(0,0)`。
- 稳态不变式 `ada_reg == pc/4` 恒成立 → 所以"之后都一一对应"。
- → 修复:**CPU 侧复位比 ROM 侧复位晚一拍释放**(新增 `resetn_1` FF,`pc_hold = !resetn_1`,`pc_next = pc_hold ? pc : next_pc`,PC 多保持一拍,if_id 用 `resetn_1` 复位)。实测 100ns 仍是 1 个气泡,110ns 正确给出 `(0, 00A00093)`。
- ⚠️ **只加"复位期间 next_pc=pc"的门控不够**(已做对照实验,仍丢 mem[0])——因为 95ns 复位一释放 `next_pc` 立刻变 4,ROM 到 100ns 才锁地址,锁到的是 word 1。**这也推翻了此前用简化 ROM 模型得到的"加一行门控即 0 气泡"的结论**,那个模型没模拟 IP 的"同步复位内部打一拍"。

**iverilog 跑 Pango IP 的两个坑(重要,下次直接用)**:
- `ipm2l_spram_v1_8_*.v:244` 的 `{{8*DATA_LOOP_NUM}{1'b1}}` 不定宽复制表达式 iverilog 不接受 → 换常量。
- iverilog **不执行"无敏感信号"的 `always @(*)`**(CS 生成块)→ `cs_bit0/cs_bit1_bus/cs_bit2_bus` 保持 X → `CSA != CSA_MASK` → `ada_reg` 永不加载、`read_en_a` 恒 0 → 输出恒 0。需加 `initial` 显式赋初值(Modelsim 无此问题)。

## 追加:用户追问"100ns 那拍 if_id_valid=1,下游会当成有效指令"

用户指出复位气泡被 `if_id_valid <= 1'b1` **无条件标成有效**,下游会执行一条幻影指令。判断正确,这是同一 bug 的**第二半**。

三个要点(已写入 `doc/取指ROM复位后丢第一条指令_原因与修复.md` 第 4.4 节):

- **`0x0000_0000` 不是 NOP,是非法指令**:RV32I 里 `opcode=7'b0000000` 未定义(规范特意把全零编码保留作非法指令,用于捕获跳到未映射内存)。真正的 NOP 是 `addi x0,x0,0` = **`0x0000_0013`**。`idu.v` 是精简版(只有 `inst_xxx` 全集判定 + `imm`,无控制输出),`opcode=7'b0000000` 不命中任何 `inst_*` → 所有控制位落默认值,默认值不全 0 就会真改状态。
- **`if_id_pc = 0` 与复位向量同形**,波形和异常上报上都分不出气泡与"pc=0 的真指令"。
- **三条约定**(建议现在就定死):① 气泡 = `valid=0`,不是"把指令字段清 0";② valid 随每级打拍(`id_ex_valid`/`ex_mem_valid`/`mem_wb_valid`);③ **每个副作用都与 valid 相与**(`rf_we`/`mem_write`/`br_taken`),这条最容易漏。冲刷时清 valid 不清指令。白送一条 `inst_illegal = ~(|所有 inst_*)`,将来接 trap 直接用。
- 两方案对照:方案二+修复在 100ns 有 1 个气泡但**已被正确标为 valid=0**;方案一-B 复位释放后第一拍就是真指令 `(pc=0, mem[0])`,**没有假有效气泡**。→ 说明 `valid` 约定**两套方案都必须做**,不是方案二专属补丁。
- 可选技巧:复位期间把 `if_id_pc` 置 `32'hFFFF_FFFF`(不可能成为 PC 的值),波形上一眼认得出气泡;但不能替代 `valid`。

### 4.4 补充:用户追问"怎么把一个气泡判成无效?是 `if_id_valid <= valid` 吗"

核心心智模型:**IF 是最前一级,没有上游 valid 可继承 —— `if_id_valid` 是 IF 级自己"制造"的**,它的 D 端 = "这一拍交给 ID 的 {pc,inst} 可不可信"。

气泡三个来源,三种不同处理(**最容易混的一处**):

| 来源 | 条件 | 处理 |
|---|---|---|
| 复位 / ROM 输出尚未有效 | `!resetn_1` | **清 0** |
| 冲刷(分支/跳转/异常) | `flush_req` | **清 0** |
| 下游阻塞 | `stall_req` | **保持原值**(不是清 0!) |

标准写法:`wire if_id_write = resetn_1 & ~stall_req; wire fetch_valid = resetn_1 & ~flush_req;` → `if (!resetn_1) 清0; else if (if_id_write) { pc<=pc_r; inst<=rdata; if_id_valid<=fetch_valid; }`

**关于 `if_id_valid <= valid`**:那种"全域 valid"(= `resetn` 打一拍,正是本工程 `topcpu.v` 里注释掉的那段)在**只有复位一种气泡来源**时与上面等价(它和 `resetn_1` 就是同一个信号);但**完全不理会 `flush_req`**,分支跳转时会把作废指令标成有效 → **不推荐用全域 valid**,要把三个来源写清楚。

下游两件事:① `id_ex_valid <= if_id_valid`(随级打拍,stall 时保持);② 每个副作用与当级 valid 相与(`rf_we`、`mem_write`、`br_taken`)。

### 4.5 补充:用户追问"复位后这一个气泡到底怎么处理"

**先分清两件事,严重程度差一个数量级:**
- **丢指令**(mem[0] 被跳过 → 程序从 mem[1] 开始跑)= **语义错误**,必须修(已由 `resetn_1` + `pc_hold` 修好)。
- **气泡**(`valid=0` 的空槽)= 只多 1 拍启动延迟,**零语义影响**;标成无效即可,**不需要"消除"**。

**关键结论:**
- 气泡不需要任何"复位专用"逻辑 —— 它和 **stall 插的气泡、分支冲刷的气泡是同一种东西**,流水线本来就得支持。处理它只有三件事(全是 4.4 的通用机制):标 valid=0 / 副作用与 valid 相与 / **不要为它写"复位后第一拍特殊处理"代码**。
- **气泡不会让后面指令错位**(只占一个槽);丢指令才会让整个程序偏移。比喻:气泡=队列多个空位,丢指令=队列少一个人、全体前移。
- **方案二里这个气泡物理上消除不掉**(ROM 同步复位内部打一拍,rst 撤销后必须过一个完整时钟才有数据)。要 0 气泡只能换**方案一-B**。
- 代价:方案二首条有效指令 110ns、方案一-B 100ns;但 5 级流水复位后本来要 4 拍填满,**吞吐率不变**(稳态每拍 1 条),只影响启动延迟。
- 三种写法:A 复位期间不写(保持)✅ / B 写进去但 valid=0 ✅ / C 写进去且 valid=1 ❌。**别用 `if_id_inst==0` 判断气泡**(靠数据认气泡,ROM 里真有全 0 就会误判),只认 `valid`。
- 省事说法:tb 里把预期从"100ns 应有 (0,00A00093)"改成"**复位释放后第一个 `if_id_valid=1` 的拍**应为 (0,00A00093)",这个气泡就不用管了。

文档:`doc/取指ROM复位后丢第一条指令_原因与修复.md` 新增第 4.5 节。**工程文件仍未改动。**

### 4.6/4.7 补充:用户追问"气泡 valid=1 会让下游使能为 1" + 已实测出他的最小修改

**用户已自行改名/改造顶层**:`myriscv/topcpu.v` **已不存在**,现在是 `myriscv/topcpu_instrom.v`(module 名 `topcpu_instrom`)。他已经把 `vaild`(= `resetn` 打一拍)加进去了:
`assign inst_sram_addr = vaild ? next_pc : pc;` + `else if (vaild) pc <= next_pc;` —— **这就是 4.2 的 `pc_hold` 方案,`mem[0]` 已经能拿回来了**。

**但 `if_id` 那个块还在用 `if(!resetn)`** → 复位释放那拍仍会写 `(0,0,valid=1)` 的假有效气泡。

**实测结论(官方 IP 模型,两组同时跑,见 `.workbuddy/sim_rom/tb_assert2.v` + `sim_assert2.log`):**

| 时刻 | 当前版 | 改一处后 |
|---|---|---|
| 101ns | **valid=1** pc=0 inst=0(假有效气泡) | valid=0 pc=0 inst=0 |
| 111ns | valid=1 (0, 00a00093) | valid=1 (0, 00a00093) |

断言 `if_id_valid && if_id_inst==0` 报错次数:当前版 **1**,改一处 **0**。
→ **最小修改就是把 `if_id` 块的 `if(!resetn)` 改成 `if(!vaild)`,一行。**

**"三道闸"原则(已写入文档 4.6,回答"valid=1 会不会让 rf_we/mem_write=1"):**
1. **源头**:气泡标 `valid=0`(三个来源:复位 / `flush_req` / `stall_req`;stall 是**保持**不是清零);
2. **数据通路**:译码器 `always @(*)` **开头统一赋默认全 0**,再 case 改写(⚠ 绝不能写没有 default 的 case 或用 assign 无兜底 → 推锁存器,使能会保持上一拍值,那才是真灾难);
3. **出口**:`rf_we`/`mem_write`/`br_taken` 与**当级 valid** 相与;**建议写操作统一放 WB 提交**,只乘 `mem_wb_valid`,闸门只有一处。
外加断言:`inst_illegal` + `if_id_valid` 组合报错 → 专门抓"气泡被误标有效";配合 `if_id_pc` 哨兵值 `FFFF_FFFF` 再加一条。

小建议:用户把 `resetn` 打一拍的信号命名为 `vaild` 名不副实(它是"复位释放后延一拍"),建议改 `rst_n_d1`/`start`。
